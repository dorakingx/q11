## 1. 目指す作品

**Q11 — Quantum Emergency Response**

プレイヤーは「量子都市」の消防指令官。ノイズを擬人化した放火犯が引き起こす量子エラーに対し、量子ゲートを通じた伝搬を理解し、火そのものではなく警報を手掛かりに消防士を派遣する。

中心となる体験:

1. ゲートを通過すると、赤いXエラーと青いZエラーが異なる方向に伝搬する。
2. 実戦では火災位置を直接見られず、スタビライザー測定の警報を読み取る。
3. 訂正を確定した後、真のエラー・選んだ訂正・残余エラーをリプレイで比較する。
4. 「警報が消えたのに論理情報を壊した」という失敗を理解する。
5. 同じ初期条件で別の判断を試して学ぶ。

作品の主軸はQuantum Unlocked。独立したゲームとしての面白さでQuantum Playgroundにも通じるものにする。ただし最終的な応募部門・重複応募可否は最新規則に照合する。

独創性は「QECを初めてゲーム化した」と主張しない。**伝搬の時間発展、隠れたエラーの推論、訂正の反実仮想リプレイ、実際のQiskit/IonQ検証が同じミッションにつながる体験**を独自の貢献として説明する。

初回30秒程度で最初の操作を理解でき、2〜3分の審査デモで中心体験が完結する設計を目指す。これは制作時間の見積もりではなく、プレイヤー体験の長さの設計値である。

## 3. ゲームの設計

### モードを明確に分ける

**Training / Replay:** 実際のエラーを表示してよい。CNOTとHを通る変化をステップ実行で見せる。

**Dispatch / Challenge:** 確定前にはシンドロームと公開される回路予定だけを見せる。真のエラー位置、論理失敗判定、秘密のfidelity、正解を示すハイライトを漏らさない。

**Debrief:** 訂正確定後に、真のエラーE、選択した訂正C、残余CE、チェック結果、論理結果を開示する。

物語上の火災、放火犯、消防士は量子モデルの比喩であることを明記する。現実の放火・消防の手順を扱わない。過度に暴力的な表現や人物被害は不要。

### 操作

- マスの選択とX/Z、必要に応じてY訂正の選択。
- 選択中の訂正案は取り消し可能。確定前のUIが秘密情報を参照しないこと。
- 複数の訂正を選んだ場合は、何が一回の訂正操作に相当するかを画面と仕様で統一。
- 再測定がある場合は、測定というアクションとして扱い、その情報とコストを明示する。隠れた正解オラクルにしない。
- 有限の資源、手数、一定のゲートスケジュールを戦略にする。無意味なクリック連打や難解な操作を要求しない。
- 通常はステップ進行または落ち着いて考えられるテンポ。演出は滑らかでも、描画フレーム速度で物理結果が変わらない。

### 必須ミッション例

1. First Alarm: 反復符号で単一Xエラーを警報から推定。
2. Red Forward / Blue Backward: CNOTにおけるX/Z伝搬。
3. Color Switch: HによるX/Z交換。
4. Blind Dispatch: 距離3surface codeでエラーを隠した訂正。
5. Two Kinds of Trouble: X/Z/Yと両種のシンドローム。
6. Silent Failure: 警報ゼロでも論理エラーが残る例と訂正後の解説。

2・3は独立した伝搬教材として実装してよい。固定符号上の本編に無関係なゲートを挿入して、同じ符号を保つかのように扱わない。

### スコア

論理情報の保存と残余シンドロームを最優先。訂正コスト・手数・ゲーム内時間を二次指標にする。

「訂正をたくさん打つほど得点」「警報さえ消せば成功」「元のエラーと同じ位置だけが唯一の正解」にしない。スタビライザーだけ異なる訂正も等価な成功として認める。

ノイズの仮定から答えが一意に決まらないミッションでは、その曖昧さを説明する。情報不足なのにプレイヤーを不合理に責める採点にしない。

## 4. 量子モデルの厳密な要件

### Pauli表現

- n量子ビットのPauliをbinary symplectic形式 `(x,z)` で表す。YはXとZの両成分。
- 誤りフレームの合成はXOR。炎が重なったら単にORで残す実装は禁止。同じPauliを二回適用したときの打ち消しを検証。
- エラーフレームの大域位相は省略してよいが、参照状態・スタビライザーの符号を必要な場面で捨てない。
- H: xとzを交換。
- S: z ^= x。
- CNOT(c,t): x[t] ^= x[c], z[c] ^= z[t]。
- 伝搬は実際のゲートを通してのみ起こる。隣接、距離、もつれそのものを理由に勝手に延焼させない。
- Pauliフレームは理想回路に対する相対誤差として扱う。理想計算を変更した場合は、参照状態・スタビライザー・論理フレームも整合させる。

### 符号と測定

- 反復符号はXノイズ限定の入門であり、任意の量子エラーを訂正する符号として紹介しない。
- 本編は距離3rotated surface code。標準的な9 data qubits、8 independent checksの構造を正しく定義し、チェックの可換性・rank・論理演算子・距離を機械検証する。
- CSSの場合は `H_X H_Z^T = 0`、rankの和が8、論理X/Zが各チェックと可換かつ互いに反可換であることをテスト。
- 全てのweight-1 Pauliを訂正できることを確認する。no-errorを含めて28パターン。
- 測定ノイズを導入するまではperfect syndrome modelと明記。測定ノイズを導入したら、生のシンドロームとラウンド間差分のdetection eventを区別。
- 火災報知器は「周囲の火の数」ではなく、対応するPauli誤りとの反可換性を検出するparity checkである。

### 成功・失敗

訂正Cと真のエラーEについてR=CEを評価する。

- Rがスタビライザー群に属する（大域位相を除く）: 成功。
- Rがスタビライザーと可換だが、その群に属さない: 論理エラー。
- Rがチェックと反可換: 残余の検出可能エラー。

GF(2)線形代数と論理パリティで判定し、特定の入力状態一つのfidelity=1だけで訂正成功としない。例えば論理Zを論理|0>だけで検査すると見逃す可能性がある。

デバッグ用の真のEはゲーム内の物理世界・検証器だけが保持し、decoderはシンドロームと公開モデルだけを入力に取る。クライアントゲームなので改造耐性のある競技システムとは主張しない。

### 独立検証

- Python/Qiskitで独立した参照実装を作り、TypeScriptの計算と突き合わせる。
- 1量子ビットH/S、2量子ビットCNOTの全Pauliパターンを検証。
- seed固定の少なくとも1000件の小規模ランダム伝搬・訂正ケースを比較。
- 選んだ符号の全単一X/Z/Y、スタビライザー残余、論理X/Z/Y、複数エラー例をテスト。
- 必要に応じて六つの論理Pauli固有状態による参照検証を行う。符号空間全体の論理判定は代数的検証を主とする。
- Clifford+Pauliの教育シミュレーションであることを明示。非Clifford、コヒーレントノイズ、一般的な実機雑音まで正確に扱うと主張しない。

- 依存バージョンを固定し、lockfileをcommit。Python側にも再現可能な依存定義を用意。
- フロントエンドへのQiskit/Python runtime全体の無理な組込みは避ける。

- 切断時にもローカルゲームは動作し、クラウド検証の失敗は適切に通知。
- コンソールの重大エラー・未処理例外がない。

見た目は実ブラウザのスクリーンショットで確認する。少なくとも開始、実戦、伝搬リプレイ、silent failure、モバイルの画像を実際に見て、崩れを修正する。

性能目標は軽快な操作、不要な大依存やネットワーク待ちの除去。計測した指標と環境を示し、未測定の60fpsやLighthouse点数を記載しない。

## 9. GitHub運用

1. `pwd`、Git status、remote、既存CLAUDE.md、認証中のアカウントを確認。
2. Q11が既に存在する場合は内容を読む。別物の同名プロジェクトを上書きしない。
3. 新規の場合はユーザー個人アカウントにprivateで作成。Organization配下に作ってHobby制約に衝突させない。
4. ユーザーの既存未commit変更を保護。無断のreset --hard、force push、履歴改変は禁止。
5. `.gitignore`、MIT LICENSE、README、設計・進捗ファイルを用意。MITファイルの追加とpublic化を混同しない。
6. 量子モデル、導入、本編、検証、デザイン、提出資材など意味のある節目でcommit/push。
7. 必須テスト失敗状態を完成版として記録しない。WIPなら明示。
8. 開発期間の記録を残す。日付偽装・開始前の成果の新規制作偽装をしない。
9. GitHub API/CLIで `isPrivate` 等の実値を再確認する。

## 10. Vercelデプロイ

- ログイン中のユーザー、plan、対象scope、project、commitを確認。
- 未使用のQ11専用projectを作成し、最初のソース転送・Git連携デプロイ前にVercel Authentication = All Deploymentsを設定。
- 本番ドメイン、preview URL、deployment URL、エイリアス、例外設定を確認。publicな例外を作らない。
- 保護されたpreviewでテストし、同じ検証済みcommitから必要なprotected productionを用意。
- 認証済みのHTTP確認には既存Vercel認証と `vercel curl` 等の公式手段を使う。
- ブラウザテストは許可済み認証方式で行い、秘密をトレースや動画に残さない。アクセスできないからと保護を切らない。
- テスト用のTrusted Sources等のアクセス拡大が必要なら、勝手に広げない。ローカルE2Eとリモート未検証を区別して報告する。
- 未認証の別ブラウザ/HTTPからはアプリ本文・API・主要静的アセットが公開されないことを確認。401/403または認証へのredirectを確認する。ログインページ自体が200を返す場合は本文を確認し、status codeだけで判定しない。
- 証拠にURL、deployment ID、git SHA、protected設定、認証あり/なしの結果を残す。bypass token付きURLは記録しない。
- 初回設定を非公開のまま完了できない場合は、ローカル成果を保存しデプロイをBLOCKEDとする。

## 11. 提出用資材

`submission/` に、少なくとも以下を作成:

- `PROJECT_PAGE.md`: 英語。問題、プレイ方法、独自性、量子機構、Qiskit/IonQとの接続、再現手順、限界、作者/帰属、実績のない宣伝を避けた説明。
- `SHORT_DESCRIPTION.md`: 1文・短文・長文の説明。実際のフォーム制限が確認できたら合わせる。
- `DEMO_SCRIPT.md`: 120〜180秒の台本と絵コンテ。最初にプレイ、次に「見えない火」「警報ゼロの失敗」、最後に量子実装と検証を見せる。
- `DEMO.mp4`: 実際に動くアプリを録画した120〜180秒の動画。必要なら字幕中心。架空UIや生成映像を動作証拠の代わりにしない。実クラウド実行をしていない場面で実行済みと演出しない。
- `ATTRIBUTION.md`: 使用ライブラリ、テンプレート、参照したコード/回路/文章、AIツール、アセットの帰属・ライセンス。
- `QOLLAB_IMPORT.md`: 実際に確認した編集・配置・実行手順。APIがない場合は手動操作を具体的に記す。
- `RELEASE_CHECKLIST.md`: 下記の公開前ゲート、公開手順、ログアウトでの最終確認、captainによる提出手順。
- `KNOWN_LIMITATIONS.md`: 未対応のノイズ、測定モデル、バックエンド、制約、未検証項目。
- `EVIDENCE_INDEX.md`: テスト、回路比較、実クラウド実行、実UI画像、private/protected確認への索引。

動画・スクリーンショットは非公開のローカルファイルとして作る。大きな動画を不用意にGit履歴へ入れず、保存先とSHA256をprivateの成果物一覧で示す。公開用動画ホストへのアップロードはユーザー承認後。

文章だけ・台本だけで「動画完成」としない。録画環境がなければ代替の自動録画スクリプト等を用意し、DEMO.mp4未完成を明記する。

### 承認後だけ実行する公開手順（今は文書化のみ）

1. 最終コミット、MIT/帰属、ソースとGit履歴の秘密情報混入を確認。
2. ユーザーが公開する対象とタイミングを明示承認。
3. GitHubをpublic化。
4. 審査用Vercel URLの保護を解除し、アプリをログイン不要にする。
5. QollabでMITプロジェクトをpublish。
6. デモ動画をログイン不要で閲覧可能にする。
7. 全リンクをログアウト状態で確認。
8. captainがteam pageから正式提出し、提出完了を確認。

承認がないまま期限が迫っても、上記の公開・提出を代行しない。

## 12. 継続作業と完了条件

最初に `docs/Q11_PLAN.md`、`docs/STATUS.md`、`docs/DECISIONS.md` を作り、未完のP0と次の具体的操作を維持する。既存CLAUDE.mdがあれば安全に追記して指示を記録する。

Plan→Implement→Run→Inspect→Fix→Commit→Deploy→Verifyを繰り返す。単に「MVPができた」「次にやるとよい」で終了しない。一方、目的のない無限改善、同じ失敗の無限再試行、未承認課金、締切後の提出物の偽装もしない。

外部要因で止まった工程があっても、独立したUI・テスト・ドキュメント・録画・パッケージ作成を続ける。認証・ユーザー承認などの外部依存以外に未完が残っている間は、完成扱いにしない。

締切直前には新機能追加を止め、データ損失防止・必須不具合修正・提出準備を優先。締切に到達したら、完了/未完・最後の安全なcommit・未実施の公開手順を報告して停止する。締切後の実装を開催期間内の成果に見せない。
